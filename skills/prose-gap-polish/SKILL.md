# 文档与逐字稿五步深度精修

把句子碎成电报体、塞满防杠补丁与括号注脚、夹杂内部自造词、存在上下文断档或前后逻辑漏洞的初稿，打磨成**零背景读者也能顺畅读懂、句式自然干练、事实与逻辑严密自洽**的定稿。收到文档后，按下面五步依次核对真实数据并改写。

---

## 第 1 步：合短碎句，去自造词与套路句

### 1.1 治理电报体短碎句
初稿常见毛病是十来个字就断句、两三句独立成段、省略主语和逻辑关联词，读起来像零散备忘录：
- **合并同类项**：把同一因果链、同一操作步骤或同一对比维度的两到四句短碎句，按因果、递进、条件或转折关系融合成完整句。
- **补全动作主体**：消除无主句（如「到时保存已确认的标签，未完成的源窗留空」→ 写明由谁在什么条件下触发什么动作）。
- **控制长句重心**：每句话只围绕一个重心推进，长句内部用分号或破折号自然换气，不堆砌多层定语。

### 1.2 消除自造词、内部缩写与套路公文腔
- **拆解生造复合词**：把代码变量名或口头生造的四字词还原成具体动作与事实（如「到龄的 72 小时回收」→「发布满 72 小时后的播放数据回收」；「源窗」→「原片起止时间区间与镜头号」；「热点信号冻结」→「生成本集热点清单」；「关键帧联系图」→「镜头抽帧拼图」；「跨账号共振度」→「多账号重合度」）。
- **解释内部代号**：首次出现内部模块或流程简称（如「反求」「主控」「避开段」）时，当场用半句话交代它做什么。
- **外文原句附中文对照**：引用外文标题、评论或台词时，紧跟括号或换行附上自然中文翻译，不让跨语种打断阅读。
- **清除禁止句式、公文黑话与不地道的外来行话**：❌ 严禁机械套用「不是……而是……」「不在……而在……」「讲的不是……」等二元对立套路句（直接正面写清是什么、怎么做）；删净「赋能、沉淀、抓手、打法、心智、推成、认知闭环、依据此项」等公文腔与「唯一底账、唯一事实源、衍生文件、落盘」等生硬工程黑话；中文创作与业务文档里遇到不地道的外来术语或中英夹杂说法（如「POV 代价」「tell 多于 show」），改成对应行业自然地道的中文表达（如「单视角局限」「转折缺铺垫、靠独白硬讲」）。

## 第 2 步：去除防御性说明、元说明与多余注脚

大刀阔斧砍掉淹没业务主线的三类赘肉：

### 2.1 砍掉防御性补丁
- **病灶**：为防极端情况被挑刺，在正文反复罗列空值兜底、异常分支、幂等细节，或把同一原则换花样叮嘱三四遍（如 ❌「若无有效百分位则记 0；平台未返回记 `null`；并列取平均名次」「以临时文件写完后原子重命名写入……若损坏则写空信号文件绝不阻塞生产」，或在每章末尾重复「无需人工手填」「不再另建独立文件」）。
- **改法**：**同一核心原则全篇只在最关键处讲透一次**；原子写文件、`null` 缺省、并列名次折算、缓存清理等常规开发卫生直接从方案正文删掉，只留影响业务决策的主链路规则。

### 2.2 砍掉作者元说明
- **病灶**：跳出内容自我解说为什么写这一段、接下来讲什么或改稿历史（如 ❌「后文反复出现这些词，先说清楚」「以下表格展示了……」「如前文第 X 节所述」「为什么本次删掉了旧版某字段」）。
- **改法**：**直接给当下要落地的结论与设计**，删掉一切对文档结构或改稿过程的自我旁白。

### 2.3 砍掉多余注脚与括号套娃
- **病灶**：一句塞两三个括号叠放代码路径、字节上限、固定列数或校验拦截提醒，或为远期设想写大段复杂阈值与补偿公式（如 ❌「集号、本地相对路径与 `video_sha256`（首次计算后缓存）必须匹配 `local_media_asset`（工作台本地媒资表）……」）。
- **改法**：**一句之内最多保留一处确有必要的括号**；能融进主干的融进主干，底层实现边角料与超前过度设计一律删净。

## 第 3 步：排查并消除四类歧义

逐段清除读者能读出两种解释的句子：
1. **代词与省略指代歧义**：前文出现两个以上人物、系统或数据集时，后句的「他 / 她 / 它 / 这 / 两者 / 对应项」必须点名具体对象。
2. **并列与修饰边界歧义**：拆开「A 和 B 的 C」等含混结构（如「保留原声对白与配乐混音」易被误读为保留原片配乐，应写准为「分离并保留原片演员对白，再与新换配乐混音」）。
3. **同名概念混用**：同一个词若在同一文档指代不同层级对象（如既把 `T1/T2` 叫模式，又把 `music_montage/dialogue` 叫模式），同场出现时必须加定语区分。
4. **统计口径与分母切换歧义**：同段出现多个百分比时（如先按「打回原因」算占比 84.7%，紧接着按「声音处理方式」算打回率 33.4%），切换处必须点明分子维度与分母基数。

## 第 4 步：站在零背景视角核对真实数据、补齐信息断点

假设读者**没看过业务原片、没读过代码仓、没参加过前序讨论**，从头顺读；凡突然冒出未交代来龙去脉的人物、事件、现有模块、变量或规则，即属信息断点：

1. **与现有系统的衔接断点**：先讲清现有项目已做到哪一步、有哪些现成资产与模块，再点明新方案在何处切入、复用了什么、补哪块短板。
2. **跨模块耦合断点**：在讲 A 的方案里顺带改 B 时，点明两者的业务依赖（如做外部归因前须先在内部审片台把打回原因拆清）。
3. **上下游数据流断点**：交代输入数据从哪来、包含什么字段（如提到「与本集反求对上」时，点明剧本反求已产出带角色名与时间码的分场剧本、多语种字幕和逐镜描述）。
4. **案例人物与前情断点**：交代案例出场人物身份、与主角关系、具体事件及入选或淘汰理由。

**补齐铁律**：若项目配有代码仓、数据库、任务产物或历史记录，**必须先检索核对真实数据与实现逻辑**（顺手纠正原稿事实错标），再用一两句前置说明自然嵌入主线，绝不凭空编造或堆砌背景百科。

---

## 第 5 步：排查并修复五类逻辑断点

审视整条业务与技术链路本身是否自洽：
1. **现有能力复用审查**：放着现成结构化数据（如台词本、镜头表、多语种字幕）或 Agent 自动化能力不用、反去设计低效纯人工环节（如人工拉进度条标时间码）的，主动改为自动化链路。
2. **过度设计收敛**：一期尚未跑通就堆砌动态阈值状态机、多层缓存淘汰、繁琐对账表或无用预留字段的，收敛为简单直接的规则。
3. **漏斗算术验算**：核算上下游吞吐量与过滤比例，确认下游评分或触发门槛在上游实际日产量下真能凑够。
4. **时序与因果顺叙**：按真实发生与触发的先后顺序叙述，禁止倒叙后再用「但」折返补条件。
5. **表文与首尾一致**：核对架构图、流程图、表格与正文的模块名、状态名和数字口径一一对应。

---

## 输出规范

1. 直接将精修定稿写入目标文件；若目标仓库带格式或链接校验脚本，跑通确认零报错。
2. 在对话中按**「项目现状衔接与架构取舍 → 去除防御性/元说明/过度设计 → 修复的信息与逻辑断点 → 语言与配图升级」**四块简明汇报核心改动。
