# 不留黑箱

> Know your own shit —— AI 做完的活，你得能讲给别人听。

Agent 一个人把活干完了，使用人却没看过材料、没跟过过程。他接下来要去和客户、同事、专家
沟通，必须先听懂：**需求从哪来、改了什么、为什么这么改、改了以后会怎样、还剩什么没定**。

本 skill 规定怎么讲：**每个事项都按同一个顺序讲**，用真实数据举例，原文和解读并排放，按读者
拆成几份文档。它不管活怎么干，只管活干完以后怎么讲清楚。

## 1. 什么时候用，什么时候不用

**用：**

- 使用人明确说自己没看过材料、要先理解，或者要拿去和别人沟通。
- Agent 独立完成了跨多份材料、多个改动的工作，使用人只看到了结果。
- 改动会影响外部的人（客户的数据、专家的方法、同事的模块），需要有人去解释。

**不用：**

- 小改动、一问一答能说清的，直接在对话里讲。
- 使用人一直全程参与，只需要一个结论。
- 使用人只要一份给外部的正式文档（报告、发布说明），那用对应的写作规范。

拿不准时，先在对话里用三五句话讲结论，问使用人要不要展开成文档。

## 2. 动笔前准备

逐项确认，缺的就补，补不到的写进文档的「未决事项」：

| 项 | 要确认什么 |
|---|---|
| 读者 | 文档给谁看：使用人自己、客户、同事、专家。每类读者一份，不要混在一起 |
| 原材料 | 使用人给过的每一份材料：文件名、谁写的、是什么性质（标准、意见、需求、笔记） |
| 事项清单 | 这一轮做了哪几件事，每件事对应哪份材料 |
| 证据 | 每个结论背后的实际数据：改前改后的值、比对结果、测试结果。**要从真实数据里取，不能凭印象写** |
| 验证 | 做了哪些验证、结果如何、哪些没验证（比如本机缺环境）|
| 未决 | 哪些需要外部的人拍板、哪些是自己后续要做的 |
| 保密 | 哪些信息不能出现在给外部看的文档里（见第 6 节）|

## 3. 文档组合

按读者拆，一般是三份，都用单文件 HTML（浏览器直接打开，不依赖外部资源，见第 5 节）：

| 文档 | 读者 | 作用 | 主要内容 |
|---|---|---|---|
| 方案说明 | 使用人 | 先吃透整件事 | 一页速览、先理解系统、需求来源、每个事项的讲解、上线与验证、未决与风险、沟通口径、名词解释、文件与记录 |
| 原材料导读 | 使用人 | 对照原材料逐份讲 | 材料之间的关系、每份材料的原文摘录和解读并排、每份材料按第 4 节的顺序讲一遍 |
| 确认单 | 外部专家或决策人 | 逐条答复 | 已处理的（不用回复）、疑似问题（附现状和建议）、需要拍板的（每条一个明确的问题），统一编号便于回复 |

不必三份都做。使用人只要理解，就先做方案说明；他说「对照原材料讲」，再做导读；有需要外部确认的
事项，才做确认单。

**使用人只要一页时**，把方案说明和导读合成一页，顺序固定为：一页速览 → 先理解系统 → 原文对照
（原文和解读并排）→ 每个事项的讲解卡 → 未决事项 → 沟通口径（需要时）→ 文件与记录。确认单始终
单独成文，因为读者不同。

## 4. 核心：每个事项按同一个顺序讲

这是本 skill 最重要的一条。使用人觉得「好懂」，主要靠这个顺序，所有事项都按它写：

1. **它是什么**：先用一两句白话解释被改的东西本身。读者不知道「分级标准」「权重」是什么，后面的改动他看不懂。
2. **原文 / 改前**：材料原话怎么写的，或者改之前是什么样。原文照录，不要转述。
3. **改成了什么**：用改前改后对照表，配真实数字的例子。一条规则配一两个最典型的例子，不要列全量。
4. **一个算给你看的例子**：挑一个具体对象，把改前改后各算一遍，让读者看到差在哪里。
5. **边界**：哪些没动、为什么没动；哪些是例外。
6. **怎么落地的**：用什么方法改的、改了多少处、碰到了什么坑、怎么处理的。
7. **影响**：对结果、对外部的人有什么影响；什么不受影响。
8. **和其他事项的关系**：它和哪份材料、哪个待确认事项、哪个后续工作有关。

不是每一步都必须有，但**顺序不要乱**。详细写法、措辞和反例见 [references/rhythm.md](references/rhythm.md)。

几条容易卡住的规则：

- **结论放在卡片前面**：每个事项先用一个结论框说一句话（改了什么、影响多大、状态），下面才是八步讲解卡。
- **原文不重复**：页面上方已经有原文并排的，讲解卡里第 2 步只写「改前是什么状态」，不再照录原文。
- **可以用假设的例子**：真实数据里找不到能说明问题的对象时，可以假设一个输入，但**分界值、公式、
  权重这些规则本身必须是真的**，并在例子旁标「假设」。能找到真实对象（样例数据、实际记录）时优先用真的。
- **再算一个不变的例子**：讲「什么不受影响」时，最好算一个改前改后结果相同的例子，比一句话有说服力。
- **规模数字写清口径**：「改了多少处」可能有两种数法（业务上的条目数、系统里的副本数），两个都写并注明。
- **使用人自己拍过板的事**：写成「按你 X 月 X 日定的口径」，提醒他这是他自己的决定，但仍然讲清内容。
- **讲解中发现的新问题**：写在对应讲解卡末尾的提示框里，同时列进「未决事项」，标明「讲解时新发现，未核实」。

## 5. 写法规则

- **结论先行**：每节第一段就是结论，依据放后面。读者只看第一段也该知道发生了什么。
- **白话**：术语第一次出现就解释；不用内部代号、提交号、函数名当主语，需要时放括号或附录。
- **真实数据**：例子里的数字从实际数据里取，写之前先查一遍。查不到就写「未核实」，不要编。
- **原文和解读并排**：左边是材料原话，右边是理解和处理结果。读者能自己判断你理解得对不对。
- **状态一眼可见**：用「已完成 / 待确认 / 未做」这类标签，不要让读者从段落里找状态。
- **诚实**：没验证的写没验证，出过的问题写出来，被推翻的结论要更正。
- **长度**：讲透为止，但不要把材料整段搬过来。表格只放有代表性的行，全量放附录或另给文件。
- **HTML 要求**：单文件，颜色走 CSS 变量并做深浅两套主题，窄屏能看，不引外部脚本。版式和组件照
  [references/page-template.html](references/page-template.html)。
- **沟通口径**：每类读者一段可以直接说出口的话，三到五句：先说结论，再说对他有什么影响，最后说需要他做什么。
  写法和例子见 [references/rhythm.md](references/rhythm.md) 末尾。

## 6. 保密与脱敏

讲解文档会被转发。动笔前先想清楚每份文档会给谁看：

- **给使用人自己的**可以写内部细节，但仍然**不写**密码、令牌、密钥、服务器地址、个人联系方式。
- **给外部的**（客户、专家）只写对方需要知道的：不写内部系统结构、其他客户的信息、实现细节、
  内部人员的评价。
- 引用材料原文时，只摘和事项有关的几行。
- 文档要放进共享仓库或作为示例复用时，**整体脱敏**：项目名、客户名、人名、行业术语、编号体系、
  真实数值、地址、提交号全部替换成虚构的，替换后通读一遍，再按名单检索一遍有没有漏网的。

## 7. 交付以后

- 把文件发给使用人，用几句话说明每份文档讲什么、建议先看哪一节。
- 主动点出两三件他沟通时值得先提的事（风险、例外、遗漏）。
- 使用人说「这个没看懂」，就单独把那一项按第 4 节的顺序在对话里讲一遍；他认可了，再把这段讲解
  补回文档对应位置。使用人说「这个节奏好」，后面的事项都照这个节奏补齐。

## 8. 自查清单

交付前逐条过一遍：

- [ ] 每节第一段就是结论
- [ ] 每个事项都按第 4 节的顺序讲，没有跳过「它是什么」
- [ ] 每个例子的数字都从真实数据里查过
- [ ] 原文是照录的，不是转述
- [ ] 状态标签和正文一致
- [ ] 未决事项写明了需要谁
- [ ] 给外部看的文档里没有不该出现的内部信息
- [ ] 文件能单独打开，深色主题下看得清，手机宽度下不横向滚动。宿主有预览或截图工具就实际看一次；
      没有就在交付说明里写明「未实测」，不要声称已检查
- [ ] 假设的例子都标了「假设」，规则数值都是真的
