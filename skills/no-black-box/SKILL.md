# 不留黑箱

Agent 独立做完一轮跨材料、跨模块的改动后，使用人往往没看过原始材料、也没跟过中间过程，却要马上去向客户、专家或同事解释。交接的目标，是让零背景的使用人顺着一份文档从头读到底就能把来龙去脉吃透：**业务原本怎么转、需求出自哪份材料、具体改成了什么、拿真实数据算出来差多少、还剩什么等谁拍板**。

| [references/evidence.md](references/evidence.md) | 引用源文件或配截图时读：精确到行列/单元格的出处写法、源文件与系统页截图规范、图注核对项 |

## 1. 适用边界与交付物组合

- **何时启用**：使用人没看过原始材料或过程，需要先吃透再对外沟通；Agent 独立完成了跨多份材料或多处逻辑的改动；改动会影响客户数据、专家规则或协作方模块。
- **何时不用**：几句话能在对话里说清的小改动；使用人全程参与、只需一句结果确认；只需正式对外发布物（如版本发布说明、评测报告）而无需交接导读。拿不准时，先在对话里用三五句话报结论，问使用人是否展开成文档。

每次交接最多产出两份文档，外加一段当前对话里的私下交接说明：

| 交付部分 | 给谁看 | 载体与定位 |
|---|---|---|
| **讲解文档**（必有，只写一份） | 使用人自读，并可直接投屏或转发给同事、专家、客户 | 默认单文件 HTML（无外部依赖、图片以 `data:` URI 内嵌）；团队日常用在线文档协作时直接写在线文档 |
| **确认单**（有外部待拍板事项才做） | 需要逐条答复或拍板的外部专家、客户或决策人 | 独立成文（单文件 HTML 或在线表格/文档），方便对方按编号逐条回复 |
| **对话私下交接**（只在当前对话发） | 仅使用人本人 | 沟通口径、当面讲解提示、谁拍过板的提醒，以及不宜外传的内部实现与排错过程 |

## 2. 动笔前盘点与内外分流红线

动笔前逐项核实以下底账；查不到的如实标为「未核实」或放进待办，绝不凭印象编造：

- **读者与流向**：讲解文档除使用人外还会转给谁；确认单由谁拍板。
- **材料与产物**：每份输入材料的文件名、作者、性质，以及全量跟踪表、确认单的存放位置。
- **真实数据与出处**：改前改后数值、公式保存值与自算结果、精确到页/行/单元格的原文位置、需配图的原件与页面截图。
- **验证范围与待办**：在哪个环境/版本、什么时间测了什么、测后是否又改过代码、哪些终端或场景未测；哪些等外部定、哪些归内部后续跟进。

**讲解文档从动笔起就默认会被转发、会被涉及的人当面看到，严格执行内外分流与保密脱敏：**

| 必须守住的边界 | 具体做法 |
|---|---|
| **严禁放进文档的私密与安全信息** | 任何文档都不写密码、令牌、密钥、私有服务器地址或未授权的个人联系方式（任务所需的公开服务入口与官方联系渠道可正常列出）。截图逐张检查，裁掉或遮住私有地址栏、账号与其他客户名称。在线文档按团队默认权限创建，不擅自开启公开链接分享。 |
| **严禁放进文档的元话术与内部过程** | 文档只放事实内容，不写「用途：本人使用」「信息截至」「今天改了哪几处」等元信息，也不写讲解顺序、时间安排、措辞建议、「现场可能被问到」。文档会流向客户或专家时，不写内部系统表结构、副本数、提交号、内部人员评价，以及上线前已自行修好且不影响读者的失误——这些全部放进对话私下交接。使用人此前拍过板的规则，文档只写「按 X 月 X 日定的口径」，是谁定的在对话里提醒。 |
| **当面看得过去的语气** | 疑似原表或外部材料有误、尚待对方确认时，一律写「疑似……请您确认」，不写指责或定性对方出错的句子；容易被追问的过渡做法直接写成平实陈述，不用质问句。 |
| **入共享库或作示例时的整体脱敏** | 若文档要放入共享仓库或做公开示例，必须把项目名、客户名、人名、行业术语、编号、数值、单元格坐标、原文特征笔误、地址与提交号整套替换为虚构内容，改完通读并按原名单全文检索清零，不能只换几个名词了事。 |

## 3. 讲解文档的五段线性结构

按零背景读者的认知顺序单向推进，**不并排摆重叠的「结论 + 一页速览」，不首尾重复列文件表，也不把同一批待定事项拆成多节重抄**。某一段确实没有内容时直接省掉：

### 第一段：全局结论与背景
1. **全局结论框**：三五句话说清本轮做完了什么、已发到哪个环境、哪些结果会变而哪些历史数据不受影响、需要谁配合做什么。
2. **业务怎么运转**：用一两段白话把被改模块原本的计分、流转或业务规则讲清楚。读者先懂底盘，后面看改动才不迷糊。
3. **材料与配套文件表（全篇唯一文件清单）**：一张表列齐输入原材料（文件名、作者、用途、存放位置）与本轮配套产物（全量跟踪表、确认单的文件名与位置/链接）。

### 第二段：逐项讲透（可按材料或事项分节）
每节开头先放一句简明结论框（改了什么、影响面、状态标签），随后按事项体量选择对应讲法（不再叠套多层重复结论框）：

- **单条规则或逻辑改动 → 原文并排 + 六步讲解卡**：
  先放一组**原文与解读并排**（左框逐字照录材料原话并标出处，右框写理解与处理结果；关键原件紧跟内嵌截图），再放一张讲解卡按固定顺序讲清（不适用的步直接省掉）：
  1. **它是什么**：一两句白话解释被改对象本身是什么。
  2. **改前与改后**：列代表性情况的改前改后对照小表（上方并排区已照录原文时，这里只写改前状态，绝不重抄原话）。
  3. **算给你看**：挑一个具体对象把改前改后各算一遍，让差额一目了然；顺手再算一个结果不变的对照例，说明什么情况不受影响。真实数据找不到合适对象时可用假设输入，但**分界值、公式、权重必须是真实规则**，并在例子旁标明「假设」。
  4. **边界与暂行口径**：哪些情况不触发改动、例外怎么算；若有待外部确认的口径，当场写明「回复前暂按 X 执行（对应确认单 待定 N）」。
  5. **落地与核对**：改动的业务条目数与实测比对结果（仅内部阅读时可补充系统副本数与实现要点，两个口径同时出现须各标清楚）。
  6. **实际影响**：对新数据、历史数据及外部协作方分别有什么影响。
  *(讲解中若新发现尚未核实的隐患，在卡片末尾放黄色提示框说明，并同步记入第四段内部待办，标明「新发现，未核实」。)*

- **几十上百条成批意见 → 本节状态统计表 + 标杆例子**：
  不逐条罗列，也不把状态表拆去文档开头：直接在本节开头放**按处理状态的条数表**（交代总条数构成，合计必须等于总数，写清每类含义与对应例号），接着给**标杆例子一览表**，再为每类挑 1–4 个标杆例子逐一配原文与解读并排框及必要截图（全量明细指向第一段文件表中的跟踪表）。

- **十来条以内的少量反馈 → 逐条处理表 + 重点项单讲**：
  一张表列清每条原话、处理结果与状态；其中涉及算账或待拍板的条目，在表下单独配一组并排框讲透。

### 第三段：上线与验证
写明发布环境、版本号与日期，测试所用版本、时间与真实样本核对结果（如几家变、几家不变，测完到发布间是否再动过代码），以及哪些终端或环节**未验证**。结论严守证据边界：重算 22 条对上 18 条、修好 4 条，就照实写清数字，绝不泛称「全部没问题」；界面行为必须对照真实代码与页面后再下笔。

### 第四段：待拍板与后续安排
把所有未结事项收拢在一处，分两小块（没有的那块省掉）：
1. **需外部确认事项（对应确认单）**：写明请谁回复、共几条、如何回复（在线文档在表内填写或评论；单文件 HTML 请对方按编号在邮件或消息里回复，如 `待定 1：按人头算`），紧跟一张汇总表列清：**编号（`疑问 N` / `待定 N`）｜事项与出处｜待确认问题或修改建议｜回复前暂行口径**。过渡期怎么做直接写在这一列，不再另起一节「补充说明」重抄。
2. **内部待办事项**：列明需内部角色后续处理的事项、说明与负责人（含「新发现，未核实」条目）。

### 第五段：附录（按需）
仅在正文放不下补充截图或确需跨部门名词表时才设附录；没有就省掉。

**跨文档一致性硬要求**：同一编号前缀只指代一类对象（写全 `例 3`、`疑问 1`、`待定 2`，不单写裸数字 `3`）；讲解文档、确认单、跟踪表里的条数、状态标签与口径表述必须完全一致，改一处时把所有关联文件同步改齐。

## 4. 确认单结构（有外部待拍板事项时才做）

没有外部待拍板事项就不做确认单。需要制作时单独成文，样式与讲解文档统一：

1. **页首说明**：写清致谁、依据哪几份材料、请回复哪几部分、回复方式（HTML 按编号回信；在线文档直接在表末「您的意见」列填写或评论）及期望回复日期。
2. **正文固定三部分**（某部分无条目则省掉）：
   - **已处理（供知悉，不用回复）**：不编号，列出本轮已改好、不用改或排入下一版的条目，写明出处、原意见及处理结果或原因。
   - **疑问（`疑问 1`、`疑问 2`……）**：疑似原材料有冲突或笔误的条目，列清编号、精确出处、系统现状（标明「疑似」）与修改建议。
   - **待定（`待定 1`、`待定 2`……）**：需要对方拍板定规则的条目，列清编号、出处、一个明确的问题（尽量给出可选项）及**回复前暂按什么口径执行**。

## 5. 交付前四视角复核与对话交接

### 交付前复核
1. **四视角独立挑错**：运行环境支持开子 Agent 时，按以下四个角度各开一个互不知情的复核者从头核查；查出的问题再交给另一名复核者尝试推翻，推不翻才改，改完对改动处复查至零新问题：
   - **事实**：逐句核对源文件原话、页行单元格、公式保存值与自算值、规则分界与状态。
   - **截图**：逐张打开核对图注与画面一致、后加红框/拼接/略去行/隐藏格均已注明，被截文档改稿后已重截。
   - **一致**：核对讲解文档、确认单、跟踪表及线上版本的条数、编号前缀与措辞完全一致。
   - **读者与纯净度**：通读检索 `本人 / 讲解顺序 / 先讲 / 时间安排 / 措辞 / 沟通口径 / 现场 / 今天` 等元词确保清零，核对被涉及方当面阅读时语气得体、无内部敏感信息泄露。
   *(无法开子 Agent 时，自己按这四个视角各独立过一遍并先尝试推翻再改，同时在对话交付说明里如实注明「未做独立复核」。)*
2. **载体与发布核验**：单文件 HTML 确认截图已内嵌可离线单开、深浅主题清晰、手机窄屏下页面不横向滚动（宽表仅在 `.tablewrap` 内滚动）、150% 放大投屏版式不乱（有浏览器或截图工具就实看一次，没有则注明「未实测」）。写入共享在线文档时，覆盖前先查有无新评论或版本号变动，发布后回读线上页确认文字与图片完整一致。

### 对话私下交接
文档就绪后，在当前对话里向使用人交付以下内容：
- **导读与未测说明**：文档位置、建议先看哪几处重点或风险，以及未执行的检查（如「未做独立复核」「真机窄屏未实测」）。
- **分角色沟通口径**：按客户、同事、专家等沟通对象，各给一段三五句能直接脱口而出的白话（结论 → 对他的影响 → 请他配合的事）。
- **现场讲解提示与拍板提醒**：当面讲的先后顺序、当着谁的面要注意的说法、可能被追问的答法，以及文档里写成「按 X 月 X 日定的口径」中哪些是使用人自己拍过板的。
- **内部技术细节**（文档需对外流转时）：具体改法、系统表结构与副本数、中途修补过的差错与提交号。
- 使用人反馈某一项没看懂时，先在对话里按六步顺序单独讲透，待他认可后再补回文档对应小节。
